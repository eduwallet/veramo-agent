# Front-end API (v2)

The v2 API for the front-end issuer application. These endpoints are authenticated with the admin bearer token of the issuer, like the [v1 API](./APIV1.md). All paths are relative to `<base URL>/<tenant>`; in a `SINGLE_TENANT` configuration the `<tenant>/` element is removed.

- POST `<base URL>/<tenant>/api/v2/create-offer`
- GET `<base URL>/<tenant>/api/v2/deferred`
- GET `<base URL>/<tenant>/api/v2/deferred/:id`
- POST `<base URL>/<tenant>/api/v2/deferred/:id`

## Create Offer

POST `<base URL>/<tenant>/api/v2/create-offer`

Creates a credential offer for one or more credentials. The offer has one grant type and at most one transaction code, which apply to all credentials. Credentials that are issued in a deferred manner and credentials that are not can be mixed in one offer.

```json
{
    "grant": "pre-authorized_code",
    "tx_code": {
        "input_mode": "numeric",
        "length": 4,
        "description": "text string"
    },
    "credentials": [
        {
            "credential_configuration_id": "GenericCredential",
            "claims": [
                { "path": ["credentialSubject", "name"], "value": "string, boolean or number" }
            ],
            "credential": "optional object containing a prefilled credential",
            "credential_callback": "optional URL to use as a callback to retrieve a prefilled credential"
        }
    ],
    "credentialMetadata": "optional object containing key-value pairs defining the metadata"
}
```

- `grant`: `pre-authorized_code` or `authorization_code`. A code or `issuer_state` is generated by the agent.
- `tx_code`: optional and only for the `pre-authorized_code` grant. `input_mode` (`numeric` (default) or `text`) and `length` (default `4`, at most 32) are optional, the `description` is required. The agent generates the code and returns it as `txCode`.
- `credentials`: a non-empty list. The `credential_configuration_id` must be a key of the `credential_configurations_supported` of the issuer metadata. The same configuration may be listed more than once, each with its own claims.
- `claims`: a list of `path` and `value` pairs, which the agent converts to the data of that credential. The `path` is a list of keys; a numeric element addresses an array index. The `value` is a string, boolean or number. For the `pre-authorized_code` grant, the claims must be complete for the credential, unless the credential is issued in a deferred manner: the back-office then supplies the remaining claims.
- `credential`: optional object containing a full credential for this credential of the offer. Some values of it will be overwritten or adjusted by the issuer during issuance. Fields that are supported, like `@context`, `name`, `description`, `credentialStatus` or `evidence`, will be interpreted if possible, other fields (including `credentialSubject`) are transported verbatim to the output. This feature is mainly used for the `VCDM` `OpenBadgeCredential` implementation and should be used with care.
- `credential_callback`: optional `http` or `https` URL, any other value results in a `400` response. It is used to validate an `authorization_code` flow authorization against an external application, which can then return a full credential or an error status. In case of errors (unauthorized, not found), the issuance of that credential is halted. If the callback succeeds, the return value is used as the preset credential, as if it was set using the `credential` attribute.
- `credentialMetadata`: optional object with settings that apply to all the credentials of the offer. The following settings are defined:
    - `expiration`: a number representing the seconds after issuance date for the credential to expire
    - `enableStatusLists`: a boolean that enables or disables generating status list information. If not specified, but status lists are configured for the issuer, status list information is generated. Set it explicitly to `false` to prevent generating status list information
    - `evidence`: an object or array containing evidence data as specified in the VCDM spec

The `credential_callback` is called using a `POST` with a JSON object (content type `application/json`). The parameters depend on the authorization flow that was performed. For a `pre-authorized_code` flow, they contain the `issuer_state`, and the issuance and expiration information of the access token. For an `authorization_code` flow, they contain all accumulated data as received from the Authorization Server, which depends heavily on the implementation of the AS.

For every credential, the agent creates a data set with the identifier `<credential_configuration_id>#<index>`, where the index is the position in the `credentials` list, for example `GenericCredential#2`. These identifiers are returned to the wallet in the `authorization_details` of the token response, see [OPENID4VCI.md](./OPENID4VCI.md#multiple-credentials-in-one-offer).

An invalid request returns a `400` with an `error` and `error_description`. The response of a valid request is the same as for the v1 API:

```json
{
    "uri": "the uri that is presented to the wallet as QR code or clickable link (same-device)",
    "txCode":  "optional, transaction code that needs to be shared out of band",
    "id": "a string value containing the unique identifier with which to refer to this offer/session"
}
```

The status of the offer can be polled with the `check-offer` endpoint of the [v1 API](./APIV1.md#check-offer). The offer is `CREDENTIAL_ISSUED` when all its credentials have been issued.

## Deferred credentials

A session can contain multiple deferred credentials, each with its own transaction. The `:id` of a transaction is `<session uuid>.<transaction id>`, as returned in the `id` attribute of the list endpoint (`GET .../api/v2/deferred`) and in the `deferred` attribute of the v1 `check-offer` response. The session uuid is the `id` returned by `create-offer`.

GET `<base URL>/<tenant>/api/v2/deferred` lists the transactions that wait for the back-office, with their `id`, `credential_configuration_id`, `status`, `createdAt` and `expiresAt`. Expired transactions are not listed. Use `?status=CREDENTIAL_READY` (or another status) to list transactions in another state.

GET `<base URL>/<tenant>/api/v2/deferred/:id` returns the details of a transaction: the `status`, `format` and `credential_configuration_id`, the number of `proofs` (holder keys) that were supplied, the `ttl` and `interval`, the `data` already known from the offer, the `claims_supplied` so far, and a list of `claims`. Every claim has a `path`, `type`, `mandatory`, `origin` and a `supply` list. The `supply` list contains the paths that the back-office can use in the `claims` of the POST for this claim; it is empty if the claim comes from the offer or authorization server only.

POST `<base URL>/<tenant>/api/v2/deferred/:id` with a body `{"claims": {...}, "status": "...", "reason": "..."}`. All attributes are optional.

- Without `status`, or with `status` `CREDENTIAL_READY`, the `claims` are validated and the credential is released. Mandatory claims must be present, claims with a `value_type` of `string`, `number`, `integer`, `boolean`, `array` or `object` must have that type, and the credential type must accept the data. If the validation fails, the credential is not released and the claims are not stored; the response is a `400` with a list of `errors`. Without `claims`, the data that is already known is validated. Claims that are not read by any `#deferred` or `#any` origin, and the names `__proto__`, `constructor` and `prototype`, result in a `400` as well.
- With `status` `CREDENTIAL_DENIED`, the credential is denied. `claims` cannot be combined with this. The `reason` is written to the log and kept with the session. The wallet gets `credential_request_denied` and the `reason` as `error_description`, limited to printable ASCII without double quotes and backslashes and at most 200 characters.
- A transaction that was already released, denied, collected or that has expired returns `409`. An unknown `id` returns `404`.
